1. The owner generates and retains an age key pair using their approved offline process. Give only the public `age1...` recipient to the sealed environment configuration. Never give the identity/private key to an agent. The owner supplies the key locally for decryption and verification only; the evaluation CLI never accepts a private key.
2. Pre-register the release thresholds, required sample sizes and camera-profile slices before release testing (archive S1-08 items 3/4; current plan sections 7.3 and 7.4). A new version is required after any candidate change. Report all earlier candidate results; no cherry-picking. Rotate fresh test athletes after three test evaluations, moving retired test athletes to dev.
3. On the GPU host, provision a separate OS account or ephemeral container with no AI coding agent, no developer shell history, and access only to the pinned engine worktree. Disable network access and unnecessary mounts. Use private encrypted ephemeral storage without snapshots/backups for decrypted material. Verify the pinned engine with `npm run check:baseline` and the existing engine/environment preflight. Do not enable dirty-tree or unverified-environment overrides.
4. Choose absolute, existing, disjoint directories outside the repository for `HITTERLOOP_EVAL_ROOT` and the decrypted sealed root. Neither directory may contain the other; neither may use symlinks/junctions. Protect both directories against other writers. These code checks do not defend against a privileged concurrent filesystem attacker.
5. Inside that sealed account only, prepare `registry-test.jsonl` (header `{"registry_version":1}`, every clip split `test`), `media/`, and `annotations/1.0.0/`. Use the existing PR13 fields and annotation schema. Do not put test entries into `registry/clips.jsonl`; it continues to accept only dev/validation.
6. Generate a fresh cryptographically random 32-byte salt, encoded as 64 lowercase hex. Call `parseTestRegistry(text)` and `buildMembership(clips, salt)` from `src/eval/sealed/membership.ts` inside the sealed environment; serialize with `canonicalJson` plus LF to `$EVAL_ROOT/registry/test-membership.json`. It contains only salt, counts, sorted salted sets and their digest. Treat this manifest as integrity-sensitive: it is not a cryptographic signature, and low-entropy values can be guessed from salted hashes. `checkLeakage` checks test IDs, source hashes and athlete groups against the clear registry.
7. Bundle exactly `registry-test.jsonl`, `media/` and `annotations/` with an owner-controlled archive tool, then encrypt to the owner's public recipient as `$EVAL_ROOT/sealed/test-split.tar.age`. The owner verifies decryption and archive contents locally. The supplied deterministic `tarBundle` can encode regular files with safe names up to 100 ASCII bytes; it does not invoke a tar binary. Destroy the temporary plaintext archive. Agents must never receive the registry, footage, labels or per-clip results (archive S1-08 item 7).

## Each owner-operated evaluation

1. Verify candidate version, pre-registration, athlete-use count and the sealed account/container restrictions. Decrypt `sealed/test-split.tar.age` locally with the owner-held key into the sealed root; reject unsafe archive paths and symlinks before extraction. The program requires `registry-test.jsonl`, `media/`, and `annotations/` there.
2. Set `HITTERLOOP_EVAL_ROOT` to the clear evaluation root and `HITTERLOOP_SEALED_ENVIRONMENT=1` only in that sealed environment. The environment variable is a procedural attestation, **not proof of isolation**.
3. With the already-provisioned age binary and pinned dependencies, run:

   ```text
   npm run eval:sealed-test -- --split test --sealed-root <absolute-private-directory> --release-candidate engine-baseline-1.0.0 --operator <opaque-operator-id> --recipient <owner-public-age-recipient>
   ```

   The operator is 8-64 letters/digits/dot/underscore/hyphen, starting with a letter or digit. The release candidate must equal the adapter engine version. Public `eval:run --split test` remains refused. Only `runSealedTest` may supply the runner's internal `sealed` option; it is not a security boundary against arbitrary code in the process. The runner itself requires `sealed.env.HITTERLOOP_SEALED_ENVIRONMENT === '1'` before any filesystem read; test mode passes its explicit env. There is no ambient-environment fallback. The strict validation preflight policy also governs sealed tests.
4. Verify the returned encrypted bundle SHA-256 and, using the owner's key inside the sealed environment, verify the archive contents before destroying decrypted data. Never send decrypted results to agents. The clear bundle is `$EVAL_ROOT/sealed/results/<run_id>.tar.age`; it holds `per_clip.jsonl` and `failures.jsonl`. There is currently no regression-list producer. Only aggregate `results/<run_id>/run.json` and the private access log are written in the clear. The aggregate is salted-scanned before writing; engine output and annotation details stay private.
5. Run `npm run eval:sealed-scan`. It must report `clean: true` and exit zero. It walks every file under EVAL_ROOT, skipping only files under `sealed/` ending in `.age`; a plain file under `sealed/` is still scanned. Findings show relative path, kind (`eval_id`, `source_sha256` or `athlete_group`) and count, never a matched value. Athlete groups are whole opaque tokens: a lowercase alphanumeric followed by 7-63 lowercase alphanumerics or hyphens; adjacent letters, digits, underscores or hyphens prevent a partial-token match. A test identifier or athlete group in a clear filename is a fixed-code refusal. Symlinks are refused even at encrypted exceptions. This scan detects known test IDs, source hashes and athlete groups, not arbitrary personal information or every encoding of an identifier; it does not replace owner review.
6. The tool removes the completed `sealedRoot/results/<run_id>` plaintext directory, including when encryption fails. During execution, scratch lives in `sealedRoot/results/.work/benchmark-*` because the content-addressed run ID is unknown until execution finishes; it is removed by the runner. Empty `.work` may remain. The decrypted test registry, media and annotations remain for the owner to destroy. Inspect interrupted outputs and destroy the entire private ephemeral storage. Recursive deletion is **not guaranteed physical erasure** on SSDs, snapshots or journaled filesystems; destroy the ephemeral encrypted volume/key according to owner policy.

## Access accounting and failures

The access log appends and syncs exactly one canonical JSON record before `runBenchmark`, including preflight and all benchmark reads of test registry, media and annotations. Only initial membership verification and leakage checks precede this record. Failed, aborted and repeated executions are counted; the record is never rolled back. If appending or syncing fails, execution does not start. A crash after logging but before engine execution conservatively counts an access.

Each record contains operator, UTC timestamp, release candidate, engine, membership digest, config SHA-256 and previous canonical line SHA-256. There is no `run_id` field or duplicate-run refusal. The deterministic config fingerprint hashes canonical JSON of the options known before execution: engine, split `test`, repeat `1`, clips `null`, cache `false`, allow_dirty `false`, allow_unverified_environment `false`, and release_candidate `true`. It excludes timestamps, filesystem locations and result-dependent values; the candidate version is recorded separately. The successful outcome returns both `run_id` and `access_record_sha256` so the owner can link the result to its access. Line hashes exclude LF; `record_sha256` is returned, not stored as a self-referential field.

Cooperating processes serialize through exclusive lock files. Each execution gets a new chained record, even with identical options and timestamp. Artifact overwrite protection remains: executing an identical candidate can fail export because its content-addressed bundle already exists, but that attempt still has its own access record. An adapter exception aborts sealed export, retaining its access record and producing no bundle or clear run.json for that failed execution. Non-sealed adapter failure behavior is unchanged.

Investigate leftover `registry/sealed-run.lock` or `registry/test-access.lock` after crashes before owner-controlled removal; do not blindly retry. A failed multi-file export can leave partial artifacts, but its access was already recorded. There is no automatic rollback, retry or cross-file transaction. Hash chains cannot detect tail truncation without an externally retained last hash; preserve owner checkpoints/public entries. After an interrupted execution with no returned outcome, derive the record hash and public table line from the retained private log inside the sealed environment, then follow the same owner publication review. Count unsuccessful attempts toward test-use limits. The previous synthetic-only log format containing run_id is rejected rather than silently rewritten; no real test records exist to migrate.

## Aggregate review and release status

Sealed PR14 scoring is **deferred**. This implementation exports `run.json`, the encrypted bundle, and the access record only; it does not generate `metrics.json` or `report.md`. The public PR14 loader still refuses test inputs. A separate sealed scoring implementation and owner-pre-registered release thresholds are required before a release verdict. No outcome constructs `sealedTest`, `passed`, or PR17 production-acceptance evidence.

Before any repository publication, the owner performs section 7.5 review of the specific aggregate artifact: suppress cells below five athletes or twenty swings; suppress cells dominated above 50% by one athlete; no per-athlete rows, extrema or clip IDs; at most two-way breakdowns without rare-attribute cross-tabs; whole-percent rates and counts rounded to the nearest five for slices under 100 swings. Clear local files are private review inputs, not approved public reports. The code's identifier scan does not implement these statistical publication rules.

Only after that review and explicit approval of the specific file does the owner paste `public_line` into `docs/evaluation/test-access-log.md`. The tool never writes into the repository. Pass/fail may only be decided against the pre-registered thresholds with section 7.4 sample adequacy and section 7.5 review; until then no production-acceptance claim is possible. Agents may see approved aggregates only.

## Enforcement boundaries

Enforced: schema/digest checks, clear-registry leakage checks, disjoint roots and symlink refusal, encrypted export requirement, disabled cache, private scratch/output placement, aggregate identifier scan, durable pre-execution access accounting and canonical chain verification, fixed CLI error codes.

Procedural: actual account/container isolation, owner key custody, pinning/provisioning the host, the encryptor implementation's cryptographic trustworthiness, absence of malicious adapters, no concurrent hostile filesystem writers, secure physical destruction, pre-registration, athlete rotation, owner reconciliation of interrupted outcomes and publication approval. The test-only XOR encryptor lives under `testing/` and is never selected by the CLI. A pluggable Encryptor is trusted; rejecting empty/identical output cannot prove encryption. Missing age fails closed; other process failures also fail closed. No database, production flags, production imports or evidence semantics change.
